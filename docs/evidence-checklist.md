# 通用取证请求单（按证据来源方）

> 对应批次：**D+ 增量 3**（`feat/d-shadow-probe`，PR #26）。目标：把「还需要谁来
> 提供什么证据」变成一份**可以直接转发**的一页清单。
>
> 一句话：**报告回答「问题在哪一层」，取证请求单回答「下一步找谁要什么、多少算正常」。**

本文只讲现状（代码以 `core/evidence.py` 与 `core/copy/evidence_checklist.json` 为准），
不写未来计划。

---

## 1. 它解决什么问题

现场最常见的卡点不是「看不出问题」，而是**跨团队拿数据**：

* 一线能抓包，但无线控制器、接入交换机、防火墙、DNS、代理、服务端的后台数据
  只有网络组/应用组能看；
* 口头说「帮忙看下交换机」通常拿不到有效数据，因为没说要哪个端口、哪个时间窗、
  哪几个计数、多少算异常；
* 反过来，网络组也会问「你这边到底看到了什么」。

取证请求单把两边对齐：清单按**证据来源方**（不是厂商/产品）组织，每项写清四件事：

| 字段 | 回答的问题 |
|---|---|
| `field` 字段名 | 要什么数据 |
| `why` 为什么需要 | 对应哪条结论、哪一层（让对方理解不是随口要） |
| `where` 在哪看 | 通用后台名或命令（无线控制器/AP 管理后台、接入交换机端口统计、防火墙会话表……） |
| `criteria` 判断标准或期望值 | 拿到后怎么判断正常/异常 |

### 1.1 为什么按「证据来源方」而不是按厂商

同一家公司可能同时用多个品牌的 AP、交换机、防火墙；按厂商组织清单会变成
「每个产品一张表」，换设备就失效，也容易把清单写成某家产品的操作手册。
按来源方组织后，**谁持有数据**决定清单归谁，具体后台叫什么由对方对应即可。

清单模板里因此**不出现任何具体厂商/产品名**（测试用 `-F` 扫描守住，见
`tests/test_evidence.py::TemplateSchemaTest.test_no_vendor_product_names`）。

## 2. 7 个维度

| # | 维度（机器码） | 谁提供 | 典型数据 |
|---|---|---|---|
| ① | 终端侧（`terminal`） | **本工具自己** | 抓包四层定位、探针基线、路径剖面（已随报告提供） |
| ② | 无线接入侧（`wireless`） | 网络组 / 无线管理员 | RSSI、SNR、协商速率、空口时延、信道利用率、漫游与认证事件 |
| ③ | 有线接入侧（`wired`） | 网络组 | 接入交换机端口状态、CRC/丢弃计数、VLAN/ACL、端口镜像 |
| ④ | 承载与出口侧（`transport`） | 网络组 / 防火墙管理员 | 会话与 NAT、策略命中、出口 RTT/丢包、QoS、VPN/专线隧道 |
| ⑤ | 名称解析与地址（`naming`） | 系统/DNS 管理员 | DNS 查询日志、响应码与耗时、服务器负载、DHCP 租约与地址池 |
| ⑥ | 加密与代理（`crypto_proxy`） | 安全组 / 代理管理员 | TLS 握手告警、证书链与有效期、代理解密策略、代理日志 |
| ⑦ | 服务侧（`service`） | 应用组 / 服务台 | 应用响应与错误率、后端依赖耗时、连接/线程水位、限流熔断、负载均衡健康 |

终端侧维度**恒出现**（工具已经采了），作用是把「这一侧不用再要」写清楚，
避免对方重复索取同一批数据。

## 3. 结论 → 维度怎么映射

映射写在 `core/evidence.py::dimensions_for()`（纯函数，可单测、可变异），规则按顺序短路：

1. **证据不足**（`verdict.level == 证据不足`，或 `sufficiency.ok is False`，或存在
   `category == 采集有效性` 的条目）→ **全部 7 维**（通用空白版）。
2. **正常且没有任何 `points`** → **空集合**（报告不出现该区块；界面仍可导出通用空白版）。
3. 其余情况逐条映射，并且**始终包含终端侧**：

| 结论线索 | 追加维度 |
|---|---|
| `L2` / `本地可达性`（ARP、本地链路） | 无线接入侧 + 有线接入侧（工具无法区分终端走哪种接入） |
| `L3` / `网络可达性` / `网络时延`（含 ICMP 不可达） | 承载与出口侧 |
| `L4` / `连接建立` / `传输质量`（重传、建连失败、零窗口） | 承载与出口侧 |
| `L7` / `域名解析` | 名称解析与地址 |
| `L7` / `TLS 会话` | 加密与代理 + 服务侧 |
| `L7` / `应用响应` 或其它 L7 类别 | 服务侧 |
| `verdict.probe_contrast` 指向对端（`TARGET_SIDE`） | 追加服务侧 |
| `verdict.probe_contrast` 指向本地（`LOCAL_SIDE`） | 追加有线接入侧 |
| 安全观察行 | 不参与映射（它不是本次网络故障的证据来源） |
| 有故障但类别无法识别 | 兜底承载与出口侧（宁可多问一份，不可漏问） |

三个真实故障类型的映射结果（`tests/test_evidence.py` 固化为用例，截图见
`d-CHECK-WRITER.md`）：

| 场景 | 维度集合 | 条目数（结论驱动） |
|---|---|---|
| L2/ARP 无应答 | 终端侧 + 无线接入侧 + 有线接入侧 | 2 + 4 + 4 = 10 |
| DNS 超时 | 终端侧 + 名称解析与地址 | 2 + 4 = 6 |
| TLS 失败 | 终端侧 + 加密与代理 + 服务侧 | 2 + 4 + 5 = 11 |

> 条目数是**模板里的条目**，不是命中的规则数；不同结论换来的是不同的维度与条目，
> 不是同一张表换个标题。

## 4. 怎么用

### 4.1 报告里

`report.render_markdown()` 在全文末尾追加「**## 九、取证请求单**」区块：

* 只在**结论驱动清单非空**时出现（正常且无问题的报告不会变长）；
* 维度小标题 + 四列表格（字段名 / 为什么需要 / 在哪看 / 判断标准或期望值）；
* 这是本批唯一的报告快照**声明例外**：离线报告也会多这一块，但区块是**纯后缀**，
  去掉「空行 + 区块」后旧报告逐字节不变（`reports/faults_demo.md` 已按新渲染重生成）。

### 4.2 界面上

诊断结果页在「接下来怎么做」之后出现「取证请求单」区块，三个按钮：

| 按钮 | 行为 | 接口 |
|---|---|---|
| 复制本次清单（纯文本） | 复制结论驱动的清单，无 Markdown 表格符号，直接发微信/工单 | `GET /api/evidence?full=0&fmt=txt` |
| 复制通用空白版 | 复制覆盖全 7 维的标准模板（不依赖本次结论） | `GET /api/evidence?full=1&fmt=txt` |
| 导出 .md | 下载 `*-evidence.md`（与报告区块同款 Markdown） | `GET /api/evidence?full=0&fmt=md` |

接口是**加法**的：只读最近一次诊断结果（`JOB["result"]`），纯计算、不写文件；
没有结果时返回可解释错误。旧版前端不调用它，行为不变。

```text
GET /api/evidence?full=0|1&fmt=md|txt
→ {"ok": true, "fmt": "txt", "full": false,
   "dimensions": ["terminal", "wired"], "content": "…"}
```

### 4.3 转发给协作部门

建议连同报告里的**三样东西**一起发：

1. 一句话结论（哪一层、哪个协议、哪个对端）；
2. 本清单（只要相关维度，别把全 7 维都甩过去）；
3. 明确的**时间窗**与**对象**（终端 IP/MAC、对端、端口、故障时间段）。

清单里已经写了「在哪看」与「判断标准」，对方按行填数据即可，不需要理解工具内部结构。

## 5. 隐私 / 不联网

* 本工具**不联网**，清单生成与复制/导出都是本地计算，不上传任何数据。
* 清单里只有**通用字段定义**，不包含运行时抓到的真实 IP/域名/用户名；
  真实值只存在于当次报告与界面。
* 转发前请自行确认：不要附带 pcap 原文件里的明文凭证、Cookie、个人信息；
  需要提供 DNS/应用日志时，只给域名、响应码、耗时等聚合字段。
* 证书只需要**链与有效期**，不要导出私钥；代理日志不要附用户身份。

## 6. 回填：本批不做（0.3.0 观察项）

对方把数据交回来后，人工回填并二次生成报告（标注「人工录入 / 来源：xx 后台」）
属于**后续批次**，本批只做「生成 + 复制 + 导出」，没有回填表单与接口。

同时登记到 0.3.0 观察项：与厂商 AC/交换机/VDI 后台做 API 对接（各厂商接口不统一，
暂不现实），仍以「人工导出 + 转发」为主。

# 网络故障诊断工作流

> 主线是**网络故障排查**，不是安全检测。目标是回答四个问题：
> **哪一层坏了 → 哪个协议 → 哪个对端 → 怎么修**。

## 一、先选路径

| 场景 | 用哪个工具 | 原因 |
|---|---|---|
| 只知道「访问某系统慢/打不开」，还没抓包 | `probe_link` | 先识别协议再分段计时（TLS/HTTP/SMB/Banner/Opaque），直接定位瓶颈段 |
| 已能复现问题，需要看丢包、重传、具体会话 | `capture_live_packets` | 抓包才能看到重传、乱序、RST、窗口等传输层细节 |
| 目标机器不能装驱动 / 没有管理员权限 | `analyze_pcap` | 让用户在自己机器上抓包后拿来分析 |
| 不知道抓哪台、想先看整体 | `scan_network_threats`（全网抓包） | 抓本机网卡全部流量，覆盖所有会话 |
| 想知道「这台机器实际在跑什么协议」 | `listen_flows` | 被动监听，输出会话表：源/目标/协议/包长/连接状态，不发任何报文 |

推荐顺序：**先 listen_flows 看全局在跑什么，再 probe_link 判断瓶颈段，最后才决定要不要抓包**。
如果体检显示 TCP 握手就慢或不通，抓包重点看 SYN/重传；
如果体检显示握手很快、首字节很慢，问题在服务端，抓包只需要确认服务端等待时间。

## 二、分层判定（核心）

| 层 | 看什么指标 | 正常 | 异常判定 | 常见原因 |
|---|---|---|---|---|
| L2 本地链路 | ARP 请求/应答 | 有请求有应答 | 多次请求无应答 | 对方关机、IP 冲突、跨 VLAN、网线/交换机端口 |
| L3 网络层 | RTT、抖动、ICMP | RTT<50ms(内网)、抖动<30ms | RTT>300ms 或抖动>80ms；出现 ICMP 不可达/超时 | 路由绕行、跨地域、链路拥塞、MTU 不匹配、防火墙 reject |
| L4 传输层 | 建连（SYN/SYN-ACK）、重传率、乱序、零窗口 | 握手<100ms、重传<0.5% | 有 SYN 无 SYN-ACK=不通；重传≥2% 影响体验，≥5% 严重；零窗口≥3 次 | 端口未监听、防火墙丢包、链路丢包、网卡双工/CRC、接收端应用处理不过来 |
| L7 应用层 | DNS 耗时/失败率、HTTP 状态码/耗时、TLS 告警 | DNS<100ms 失败 0；HTTP<800ms 无 5xx | DNS>300ms 或失败率≥20%；HTTP 有 5xx 或 P95>3s | DNS 服务器远/过载、域名配错、服务端报错、证书问题、下游依赖慢 |

### 协议识别规则（决定后续怎么测）

体检建连后先不发数据，用 `MSG_PEEK` 读首包，再结合端口画像：

| 首包特征 | 协议 | 后续动作 |
|---|---|---|
| `0x16 0x03` | TLS | 做 TLS 握手 + HTTPS 首字节 |
| `HTTP/`、`GET ` | HTTP | 发明文 GET 看 TTFB 与状态码 |
| `\xfeSMB` / `\xffSMB`（445/139） | SMB | SMB2 NEGOTIATE，看协商状态码（不是 TLS！） |
| `SSH-`、`220 `、`+OK`、`0x0A` 握手包 | SSH/FTP/SMTP/POP3/MySQL | 只读 banner，报响应延迟 |
| `\x03\x00\x00`（3389） | RDP | X.224 连接请求 |
| 都没有 | Opaque TCP | 只报建连延迟，不硬下结论 |

若首包与端口冲突（例：443 上返回明文 `HTTP/`），**以首包为准**并说明「该端口不是 HTTPS」。

### 关键判据：区分「网络慢」和「服务端慢」

```
握手/RTT 小 + 首字节(或服务端等待)大  →  服务端处理慢（查应用、数据库、下游）
握手/RTT 大 + 首字节也大              →  链路慢（查路径、带宽、运营商）
有 SYN 无响应 / 有 ICMP 不可达        →  不通（查端口、防火墙、路由）
重传率高、RTT 抖动大                  →  丢包（查网线、交换机、无线、双工）
```

## 三、固定输出格式（顺序不能变）

### 1. 故障定位（一句话）

`【层】+【协议】+【对端】+【现象】+【要不要立刻处理】`

例：`L4 传输层 TCP：到 10.0.0.5:8080 的建连完全无响应，业务不可用，需立即处理。`

紧接着给四层状态表：

| 层次 | 协议 | 状态 | 关键指标 |
|---|---|---|---|
| L2 本地链路 | ARP | 正常/注意/异常 | ARP 无应答 N 个 |
| L3 网络层 | IP/ICMP | ... | RTT 均值/抖动/ICMP |
| L4 传输层 | TCP | ... | 重传率/建连失败/握手 |
| L7 应用层 | DNS/HTTP | ... | DNS 均值/失败率、HTTP 均值/5xx |

### 2. 问题详解（每条四段）

```
**N. 问题标题**（严重程度）
- 所在层 / 协议 / 对端：
- 看到的现象：用户实际会看到什么（打不开、转圈、卡顿、报 500）
- 专业依据：原始数值 + 帧号 / Stream 编号
- 怎么处理：具体命令或检查项
```

### 3. 处置步骤（编号，按排查顺序）

自下而上：**先确认通不通 → 再看丢不丢包 → 再看应用**。
第 1 条必须是最先做、且做完能验证有没有效果的。

### 4. 技术明细（不得省略）

会话明细（每个 Stream 的客户端/服务端、包数、握手、RTT、重传、服务端等待、帧号）、
DNS 逐条解析耗时与 rcode、HTTP 请求逐条耗时与状态码、ICMP 明细、采集概况。

末尾附机器摘要：

```json
{"target": "<IP或全网>", "critical_count": 0, "warning_count": 0,
 "retrans_rate": 0.0, "dns_fail_rate": 0.0, "rtt_avg_ms": 0, "http_avg_ms": 0, "conn_fail": 0}
```

## 四、可用工具

| 工具 | 用途 | 关键参数 |
|---|---|---|
| `probe_link` | 协议自适应分段体检，定位瓶颈段 | `target`（可带端口）、`port`、`count`、`proto`（http/tls/smb/rdp/ssh/opaque） |
| `listen_flows` | 被动监听，输出会话表 | `target`（IP/CIDR，可空）、`duration`、`interface`、`engine` |
| `list_interfaces` | 列出可抓包网卡 | 无 |
| `capture_live_packets` | 定向抓包 + 分层诊断 | `target_ip`（可空）、`duration`、`interface` |
| `scan_network_threats` | 全网抓包 + 分层诊断 | `duration`、`interface` |
| `analyze_pcap` | 离线分析已有抓包 | `pcap_file`、`target` |
| `doctor` | 检查 tshark/Npcap/权限 | 无 |

## 五、撰写要求

- 只写工具返回的事实，禁止臆造 IP、端口、帧号与数字。
- 所有数字原样保留，不许含糊成「较多」「若干」。
- 白话层出现术语要就地解释，例如「零窗口（接收方缓冲区满了，发送方只能停下等）」。
- 只给 1～3 个最可能成因，按可能性排序；证据不足时写「需补充证据」并说明下一步抓什么。
- 安全观察（明文凭证、高危端口外联）只作附带项，**不要抢主线**；没有网络故障时一句话带过。
- 报告落盘到 `reports/`，文件名与抓包文件同名（`.md` / `.json`）。
